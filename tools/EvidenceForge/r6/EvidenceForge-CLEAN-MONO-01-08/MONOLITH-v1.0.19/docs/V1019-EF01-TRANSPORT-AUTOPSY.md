Aucun signal fetch standard ne prouve que zéro octet a été envoyé. Un ENOTFOUND déclaré par une exception n'est pas une attestation de non-acceptation.
3. Injecter timeoutPolicy.timeoutMs sur une copie de requête ; providerRegistry reste intact. Les deux kits ont une policy vide. Une valeur explicite valide prime ; valeur invalide refusée avant départ.
4. MONO-04 reprend EXTERNAL_TIMEOUT/EXTERNAL_NETWORK_ERROR et HTTP429/5xx. Il efface son timer avant response.text. Toute exception fetch est écrasée en NETWORK_ERROR. Donc un simple wrapper de résultat arrive trop tard pour empêcher une réémission.
5. Solution retenue : une seule tentative Gateway pour les appels ciblés ; les reprises admissibles restent dans le fetch décoré (maximum 2, backoff 2000ms, contrat versionné). MONO-04 garde secret, sérialisation, validation, cache d'idempotence et circuit-breaker. Pas de changement de requestId/payload. Le circuit compte désormais les appels logiques EF-01, pas chaque refus transitoire. Les départs physiques ont leur propre trace.
6. Ambiguïté dès l'invocation fetch, faute d'attestation d'absence d'envoi. Timeout/envoi interrompu/body incomplet : UNKNOWN et aucune reprise. HTTP5xx/504 ne prouve pas une non-acceptation : pas de retry. Parsing invalide : pas de reprise transport, pas de succès.
7. Seul refus sûr repris dans V1 : HTTP429 + enveloppe JSON type=error/error.type=rate_limit_error, sans usage/id/content, content-type JSON. Le contrat de cette catégorie est refus avant génération. HTTP429 seul ou corps illisible n'est pas une preuve suffisante. Refus locaux avant fetch (configuration/secret/budget) : aucun départ, pas de retry inutile. Aucun classement par message d'exception arbitraire.
8. Une issue inconnue crée une entrée KIT_CALL interrupted/usageIncomplete avec usage null, cost null/priced false selon le ledger existant. Les usages reçus restent comptabilisés. Le budget LIMITED existant bloque les appels ultérieurs non tarifés. Totaux historiques = somme connue, pas vérité du débit distant. Aucune nouvelle comptabilité scientifique.
9. EF-01B et C1 partagent la même composition ; le fence-adapter conserve le seul enregistrement du succès. La trace transport est indépendante, sans prompt/secret/réponse brute. Pipeline inchangé : LLM_PROVIDER_UNAVAILABLE enveloppe la cause technique, STOPPED ; aucune reprise automatique du kit pour ce code.

Politique proposée : EF01_TRANSPORT_POLICY_V1, contrat explicite JSON bufferisé. Response-start budget 180000ms aligné sur la fenêtre LLM existante (choix produit, non mesure de latence et non promesse du Worker), lecture du corps 90000ms alignée sur la tolérance de lecture existante, ici borne TOTALE après headers. Le budget response-start inclut les éventuels refus sûrs lus et backoff avant les headers terminaux ; il n'est jamais réarmé par un retry. Lecture bornée même si fetch/text ignore AbortSignal. Bornes strictes 1000..900000ms, maxAttempts=2, backoff=2000. Aucun SSE requis, aucun timeout global provider modifié.

Ces choix sont des contrats candidats à auditer hors ligne, pas une autorisation de smoke ni une garantie du temps de génération distant. Le défaut 8500ms sera reproduit par le vrai Gateway et les vrais kits avec horloge virtuelle.

## Affinement découvert par le test TP-10

Le test exécuté contredit l'hypothèse du point 8 : le ledger historique normalise usage null en compteurs nuls et prix zéro si le modèle est tarifé. Extension minimale nécessaire dans le ledger du NOUVEAU monolithe seulement : opt-in transportOutcome=EXTERNAL_OUTCOME_UNKNOWN, kind=KIT_CALL et usage absent donnent usage=null/cost=null/priced=false. Tous les anciens appels et les usages connus conservent le calcul historique. Aucun budget, tarif ni lot gelé modifié.

## Composition finale après contrôle des assertions historiques

Deux assertions historiques exigent stage-ef01 et le builder vendored byte-identiques. Elles ne sont pas affaiblies. Le point final est donc l'adaptateur monolithe EXISTANT mono04-fence-adapter, qui reçoit déjà cost.stage=DISCIPLINES/PLAN et les ports registry/secretProvider de l'instance construite par le builder. Il compose une instance du Gateway gelé avec le même registre et le même secretProvider, et le fetch décoré. stage-ef01 et build-real-mono04 sont restaurés byte-identiques à v1.0.18. Le transport non ciblé sera délégué au Gateway original. Aucun hook global ni patch du lot.
