# Plan de migration — 2 millions de lignes vers la nouvelle base clients

## 1. Principes directeurs

- Ne jamais charger directement les fichiers dans les tables métier.
- Conserver les trois fichiers sources de manière **immuable**, horodatée et avec empreinte SHA-256.
- Traiter chaque ligne avec un identifiant technique unique :  
  `source_fichier + numéro_ligne + version_fichier`.
- Rendre les traitements **idempotents** : une relance ne doit ni dupliquer ni altérer les données déjà validées.
- Séparer les zones :
  1. **Raw** : copie fidèle des fichiers ;
  2. **Staging** : données typées et normalisées ;
  3. **Golden/Consolidation** : clients dédoublonnés ;
  4. **Cible** : base clients opérationnelle.
- Produire une traçabilité complète entre chaque client cible et ses lignes sources.
- Chiffrer les fichiers et données temporaires, limiter les accès et purger les zones intermédiaires selon les règles RGPD.

## 2. Phases, livrables et dépendances

| Phase | Activités principales | Livrables / jalon de sortie | Dépendances |
|---|---|---|---|
| 0. Cadrage | Périmètre, volumétrie, contraintes, fenêtre de migration, SLA, RGPD, propriétaires des données | Plan validé, RACI, critères d’acceptation | Aucune |
| 1. Profilage des sources | Comptage, formats, encodages, nullité, distributions, doublons, anomalies | Rapport de profilage et inventaire des données | Phase 0, accès aux fichiers |
| 2. Mapping et règles | Correspondance source-cible, conversions, qualité, dédoublonnage, survivance | Dictionnaire de données et règles signés | Phases 0–1, schéma cible stable |
| 3. Construction | Zones Raw/Staging/Golden, ETL/ELT, journalisation, rejets, contrôles | Pipeline versionné et automatisé | Phase 2, environnements disponibles |
| 4. Tests unitaires et techniques | Parsing, transformations, qualité, dédoublonnage, reprise, performance | Rapport de tests techniques | Phase 3 |
| 5. Répétition complète | Chargement des 2 M de lignes sur environnement de préproduction | Bilan de répétition, corrections, durée réelle | Phase 4, données représentatives |
| 6. Recette métier | Validation d’échantillons et de scénarios métier | PV de recette / décision Go-No Go | Phase 5 |
| 7. Migration finale | Gel ou capture du delta, sauvegarde, exécution, réconciliation | Base chargée et contrôles conformes | Phase 6, fenêtre validée |
| 8. Bascule et surveillance | Activation applicative progressive, suivi fonctionnel et technique | Acceptation définitive | Phase 7 |
| 9. Clôture | Documentation, archivage, purge contrôlée, bilan | Dossier de migration final | Fin de période de garantie |

### Chemin critique

`Profilage → Mapping signé → Pipeline → Répétition complète → Recette → Go/No Go → Migration finale → Réconciliation → Bascule`

Le schéma cible, les règles de fusion et les critères d’acceptation doivent être stabilisés avant la répétition complète.

## 3. Profilage et préparation des fichiers

Pour chaque fichier :

- Vérifier le nom, la date, la taille, l’encodage, le séparateur et l’empreinte.
- Compter :
  - lignes physiques ;
  - enregistrements lisibles ;
  - lignes vides ;
  - lignes rejetées ;
  - clés distinctes ;
  - doublons internes.
- Identifier les variations de format :
  - dates ;
  - téléphones ;
  - civilités ;
  - pays et codes postaux ;
  - caractères spéciaux ;
  - adresses électroniques ;
  - valeurs sentinelles telles que `N/A`, `-`, `00000000`.
- Établir une matrice de qualité par colonne : complétude, validité, unicité et cohérence.

Tout écart entre le nombre de lignes fourni et le nombre de lignes lu doit être expliqué avant la poursuite.

## 4. Mapping et règles de qualité

Chaque champ cible doit avoir une règle documentée :

| Élément | Exemple de règle |
|---|---|
| Type | Conversion explicite ; aucune troncature silencieuse |
| Chaînes | Suppression des espaces périphériques, normalisation Unicode |
| Noms | Conservation de la valeur originale et création d’une version normalisée |
| E-mail | Minuscules, validation syntaxique ; domaine non corrigé automatiquement |
| Téléphone | Normalisation E.164 lorsque le pays est connu |
| Dates | Format ISO 8601, rejet des dates impossibles |
| Pays | Conversion vers un référentiel ISO |
| Valeurs absentes | Conversion des valeurs sentinelles en `NULL` |
| Consentement | Pas de consentement déduit ; valeur la plus restrictive en cas de conflit |
| Longueur | Rejet ou traitement explicite, jamais de troncature non tracée |

### Classification des règles

- **Bloquantes** : ligne impossible à identifier, format illisible, clé métier absente si obligatoire, consentement incohérent.
- **Corrigeables automatiquement** : espaces, casse, formats standardisables.
- **Non bloquantes** : téléphone absent, civilité inconnue, donnée facultative invalide.
- **À arbitrage métier** : conflits entre sources, clients homonymes, consentements divergents.

Les lignes rejetées sont placées dans une table dédiée avec le code d’erreur, le champ concerné, la valeur originale et l’identifiant source.

## 5. Contrôle des doublons

### 5.1 Niveaux de détection

1. **Doublons techniques**  
   Même fichier, même ligne ou même empreinte d’enregistrement.

2. **Correspondances exactes**  
   Par exemple :
   - identifiant client historique ;
   - e-mail normalisé ;
   - téléphone normalisé ;
   - combinaison nom + prénom + date de naissance + code postal.

3. **Correspondances probabilistes**  
   Rapprochement sur nom, prénom, adresse et date de naissance avec score de similarité.

### 5.2 Seuils proposés

- Score élevé : fusion automatique.
- Score intermédiaire : file de revue métier.
- Score faible : conservation en clients distincts.

Les seuils doivent être calibrés à partir d’un échantillon annoté. Une fusion probabiliste ne doit pas reposer uniquement sur le nom et le prénom.

### 5.3 Règles de survivance

Ordre de priorité à faire valider :

1. source déclarée « système de référence » ;
2. valeur vérifiée ou certifiée ;
3. valeur la plus récente ;
4. valeur la plus complète ;
5. en cas de conflit non résolu, conservation des deux valeurs dans l’historique et revue manuelle.

Pour les consentements et oppositions, appliquer la règle juridique la plus restrictive.

### 5.4 Traçabilité

Créer :

- un identifiant client cible pérenne ;
- une table de correspondance `source_id → client_cible_id` ;
- une table des décisions de fusion ;
- le score, la règle et la version de l’algorithme utilisés ;
- un historique des anciennes valeurs.

## 6. Stratégie de chargement et de reprise

### Découpage

Traiter les données par lots, par exemple de **50 000 à 100 000 lignes**, ajustés après tests de performance.

Chaque lot possède les états :

`REÇU → VALIDÉ → NORMALISÉ → DÉDOUBLONNÉ → CHARGÉ → RÉCONCILIÉ`

### Mécanisme de reprise

- Checkpoint après chaque étape et chaque lot.
- Commit par lot, pas de transaction unique pour les 2 millions de lignes.
- Clé d’idempotence empêchant un double chargement.
- Conservation des résultats intermédiaires jusqu’à acceptation.
- Reprise depuis le dernier checkpoint valide.
- Possibilité de rejouer :
  - une ligne ;
  - un lot ;
  - un fichier ;
  - l’ensemble de la migration.
- Journal d’exécution contenant version du code, paramètres, fichiers, compteurs, erreurs et durées.

Les corrections doivent produire une nouvelle version des règles ou des données, sans modification manuelle non tracée en base.

---

## 7. Stratégie de bascule

### Option recommandée

1. Réaliser une répétition complète.
2. Avant migration finale, prendre une sauvegarde cohérente de la cible.
3. Geler les modifications des sources pendant la fenêtre de migration, ou extraire un delta horodaté.
4. Charger les données dans des tables cibles non actives.
5. Exécuter les contrôles de réconciliation.
6. Basculer par changement de schéma, vue, alias ou configuration applicative.
7. Maintenir l’ancien système en lecture seule pendant la période de garantie.

Si un gel est impossible, définir un mécanisme de delta avec une date de coupure, puis rejouer les créations et modifications intervenues après l’extraction initiale.

## 8. Plan de tests

### Tests unitaires

- Lecture de chaque format de fichier.
- Conversion de types.
- Normalisation des noms, e-mails et téléphones.
- Traitement des valeurs nulles et sentinelles.
- Calcul des scores de rapprochement.
- Règles de survivance.
- Gestion des rejets.

### Tests d’intégration

- Chaîne complète Raw → Staging → Golden → Cible.
- Contraintes de clés et intégrité référentielle.
- Compatibilité avec les API et applications consommatrices.
- Traçabilité source-cible.

### Tests de qualité et réconciliation

Pour chaque fichier, lot et état :

- `lignes lues = lignes acceptées + lignes rejetées` ;
- aucun enregistrement perdu sans motif ;
- nombre de clients cibles expliqué par les fusions ;
- comparaison des totaux et distributions avant/après ;
- contrôle des champs obligatoires ;
- contrôle des doublons résiduels ;
- vérification manuelle d’échantillons aléatoires et à risque.

### Tests de performance

- Chargement complet de 2 millions de lignes.
- Temps de dédoublonnage.
- Consommation CPU, mémoire, espace et journaux.
- Performance des requêtes et API après migration.
- Vérification que la durée reste inférieure à la fenêtre de bascule avec une marge d’au moins 20 à 30 %.

### Tests de robustesse et reprise

- Arrêt volontaire au milieu d’un lot.
- Perte temporaire de connexion à la base.
- Fichier corrompu ou incomplet.
- Relance du même lot.
- Rejeu complet.
- Vérification de l’absence de doublons après reprise.

### Tests métier et sécurité

- Recherche et modification d’un client.
- Gestion des consentements.
- Consultation de l’historique.
